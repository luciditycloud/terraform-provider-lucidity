# terraform-provider-lucidity

Terraform provider for Lucidity (cloud storage optimization platform). 
Published to the public Terraform Registry as a community provider, built to Partner-tier quality

About Lucidity - https://www.lucidity.cloud/




```hcl
terraform {
  required_providers {
    lucidity = {
      source  = "luciditycloud/lucidity"
      version = "~> 0.1"
    }
  }
}
```



## Provider facts

- **Language/stack:** Go + Terraform Plugin Framework (NOT legacy SDKv2).
- **License:** MPL-2.0.
- **Publishing:** community provider from the Organization's GitHub repo.
  Releases signed with a dedicated GPG key held by the organization.
- **API docs:** `docs/api/` contains the three Lucidity API reference PDFs
  (auth refresh, getting started, Public Tenant API). Treat these as the source
  of truth for endpoints, fields, and error tables.

## Provider Authentication Management


1. Log into the Lucidity Dashboard
2. Click on settings (Bottom left)
3. Click on "API Key"
4. Click on "Create Key" to generate a refresh token
5. Supply the refresh token to this provider

**API documentation notes (authentication).** Differences between Lucidity's
API docs ([apidocs/legacy/auth.md](apidocs/legacy/auth.md)) and this
provider, and gaps the docs reveal:

| Topic | API docs | This provider | Impact |
|---|---|---|---|
| Where the refresh token comes from | Getting Started: an Admin generates it under Users → their own entry → Generate New Key. API reference: "issued by Lucidity CS". | The steps above (Settings → API Key) | The API docs are marked "stale" on the docs site; the steps above may reflect a newer dashboard. Use whichever your dashboard shows. |
| Who can create a token | Admins only, and only for their own account | — | Every automation runs as one named Admin. If that person leaves or loses the Admin role, the token stops working. Machine credentials (service accounts or OIDC) are needed from Lucidity's API to fix this. |
| Token lifetime | Refresh token 30 days by default; access token 15 minutes | Renews the access token 3 minutes early; never stores either token | Rotate the refresh token before 30 days. |
| Error format | Refresh errors are a flat `{code, message, details}`; other endpoints wrap errors in `{success, data, error, requestId}` | Accepts both formats and shows `details` when present | None. |

The provider takes the refresh token via (exactly one) of the following:
1. `refresh_token` (to pull from a data source)
2. `refresh_token_file` (to pull from a safely maintained file)
3. `refresh_token_command` (generic hook that covers every backend)
4. `LUCIDITY_REFRESH_TOKEN` env var 

— see `internal/provider/provider.go` for the full schema.



**AWS Option 1 - Secrets Manager (recommended):**

`refresh_token_command`, via the AWS CLI

```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://www.web.lucidity.dev/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token_command           = "aws secretsmanager get-secret-value --secret-id lucidity/refresh-token --query SecretString --output text"
}
```

Runs at configure time; the token never touches `.tf` files or Terraform
state. Requires the AWS CLI installed wherever `terraform` runs, AWS
credentials available in that environment (instance profile, IRSA, SSO
profile, etc.), and an IAM policy granting `secretsmanager:GetSecretValue` on
that secret's ARN. If the secret is stored as JSON rather than a plain
string, pipe through `jq`: `... --output text | jq -r .token`.


**AWS Option 2  -  `refresh_token`, fed from a data source**

```hcl
provider "aws" {
  region = "us-east-1"
}

data "aws_secretsmanager_secret_version" "lucidity_refresh_token" {
  secret_id = "lucidity/refresh-token"
}

provider "lucidity" {
  lucidity_dashboard_url          = "https://www.web.lucidity.dev/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token                   = data.aws_secretsmanager_secret_version.lucidity_refresh_token.secret_string
}
```

Works, but the fetched value gets written into Terraform state as that data
source's attribute (every data source result is persisted to state, not just
resources) — only as safe as your state's encryption/access controls. Also
requires configuring the `aws` provider just for this lookup.

Option 1 is preferred for exactly that reason: no bespoke per-backend client
code in the provider, and the secret never lands in state.

**Azure Option 1 - Azure keyvault (recommended):**

`refresh_token_command`, via the Azure CLI

```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://web-azurepls.lucidity.cloud/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token_command           = "az keyvault secret show --vault-name my-vault --name lucidity-refresh-token --query value -o tsv"
}
```

Requires the Azure CLI installed and authenticated (`az login`, a managed
identity, or a service principal already logged in) wherever `terraform`
runs, and the "Key Vault Secrets User" role (or a classic access policy with
`get` permission) on that secret.

**Azure Option 2: `refresh_token`, fed from a data source**

```hcl
provider "azurerm" {
  features {}
}

data "azurerm_key_vault" "this" {
  name                = "my-vault"
  resource_group_name = "my-resource-group"
}

data "azurerm_key_vault_secret" "lucidity_refresh_token" {
  name         = "lucidity-refresh-token"
  key_vault_id = data.azurerm_key_vault.this.id
}

provider "lucidity" {
  lucidity_dashboard_url          = "https://web-azurepls.lucidity.cloud/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token                   = data.azurerm_key_vault_secret.lucidity_refresh_token.value
}
```

Same state-encryption caveat as the AWS data-source option: the fetched
value is persisted to Terraform state as this data source's attribute.


**GCP Option 1 - Secrets Manager (recommended):**

```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://app.lucidity.cloud"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token_command           = "gcloud secrets versions access latest --secret=lucidity-refresh-token"
}
```

Requires the gcloud CLI installed and authenticated (Application Default
Credentials or a service account already active) wherever `terraform` runs,
and `roles/secretmanager.secretAccessor` on that secret.

**GCP Option 2: `refresh_token`, fed from a data source**

```hcl
provider "google" {
  project = "my-project"
}

data "google_secret_manager_secret_version" "lucidity_refresh_token" {
  secret = "lucidity-refresh-token"
}

provider "lucidity" {
  lucidity_dashboard_url          = "https://app.lucidity.cloud"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token                   = data.google_secret_manager_secret_version.lucidity_refresh_token.secret_data
}
```

Same state-encryption caveat as the other data-source options above.


**AWS/Azure/GCP Option 3  -  HashiCorp Vault**


```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://www.web.lucidity.dev/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token_command           = "vault kv get -field=token secret/lucidity"
}
```

Requires the Vault CLI installed wherever `terraform` runs, and Vault
authentication already established in that environment (`VAULT_ADDR` +
`VAULT_TOKEN`, AppRole, or whichever auth method your setup uses — the
provider just execs `vault`, it doesn't manage Vault auth itself), plus a
Vault policy granting `read` on that KV path.


**Option 4 (AVOID)  -  Hardcode token**

- **Avoid hardcoding the refresh token directly in a `.tf` file.** Even if you
  remove it later, it stays in your git history in plaintext forever.
- **Avoid `.tfvars` files for it.** Treat the `.tfvars` file exactly like the direct `refresh_token`
  attribute — same plaintext-on-disk risk — keep it out of version control
  (`.gitignore`), and prefer the `LUCIDITY_REFRESH_TOKEN` env var or one of
  the `refresh_token_command` recipes above instead.
- Token can be hardcoded in during testing. Remember to expire the token via the Lucidity Dashboard once testing is completed


## Lucidity Dashboard Account Management

Manages a cloud account as a Lucidity tenant: onboard it, modify it, deboard it.
Two objects: the `lucidity_tenant` resource and the `lucidity_tenants` data source.

| Cloud | Onboard (new) | Modify / deboard / import |
|---|---|---|
| AWS | Supported | Supported |
| Azure | Not yet supported by Lucidity | Supported — bring it in via `terraform import` |
| GCP | Not yet supported by Lucidity | Supported — bring it in via `terraform import` |

### Onboarding a new AWS account

```hcl
resource "lucidity_tenant" "example" {
  lucidity_dashboard_display_name = "example-account"
  lucidity_product_list           = ["AUTOSCALER"]

  cloud_entity_information {
    cloud_provider            = "AWS"
    cloud_provider_account_id = "123456789012"
    aws_iam_external_id       = "8f14e45f-ceea-4331-9f5e-111111111111" # generate your own; must match the IAM role's trust policy
    aws_iam_role_name         = "LucidityRole"
    aws_iam_policy_name       = "LucidityPolicy"
  }

  # Safety rails — defaults shown explicitly for visibility in code review.
  # Deboarding on Lucidity is IRREVERSIBLE via API: an INACTIVE tenant can
  # only be reactivated by Lucidity support, and deboarding an account with
  # running services causes immediate disruption.
  lucidity_dashboard_account_delete_protection = true
  # lucidity_account_destroy_behavior = "forget"   # consulted only if protection = false
}
```

Azure and GCP account onboarding is not supported yet — only AWS accounts
can be onboarded through this provider today (see the support table above).

### Modifying a tenant

| Field | Updatable in place? |
|---|---|
| `lucidity_dashboard_display_name` | Yes |
| `aws_iam_role_name` / `aws_iam_policy_name` (AWS) | Yes |
| `azure_service_principal_id` / `azure_directory_id` (Azure) | Yes |
| `cloud_provider`, `cloud_provider_account_id` | No — different tenant, forces replace |
| `aws_iam_external_id` | Yes — Lucidity returns and accepts it now. **Update your IAM role's trust policy first**, then change the value: Lucidity re-validates by assuming the role and rejects the update otherwise |
| `lucidity_product_list` | No — not supported by Lucidity's update API; changing a value already in state forces replace |
| `aws_org_root_id` | No — no update mechanism exists yet; changing a value already in state is caught at `terraform plan` |

### Deboarding an account (`terraform destroy`)

Deboarding is **irreversible** — only Lucidity support can reactivate an
INACTIVE tenant. Three-tier safety model:

| `lucidity_dashboard_account_delete_protection` | `lucidity_account_destroy_behavior` | Result |
|---|---|---|
| `true` (default) | — | Hard error, no API call |
| `false` | `"forget"` (default) | Removed from Terraform state only — stays ACTIVE on Lucidity |
| `false` | `"deboard"` | Actually deboards the account — the only path to it |

### Listing tenants

```hcl
data "lucidity_tenants" "all" {}

output "active_tenant_ids" {
  value = [
    for t in data.lucidity_tenants.all.tenants : t.tenant_id
    if t.status == "ACTIVE"
  ]
}
```

### Importing an existing tenant

```sh
terraform import lucidity_tenant.<name> AWS/<account-id>
```

Write a resource block for the account first, then import. Import reads the
tenant's `aws_iam_external_id` and display name from Lucidity, so they no
longer need to be guessed; a mismatch with your config is reconciled in
place on the next `apply`. `lucidity_product_list` and `aws_org_root_id` are
not returned by Lucidity's List API yet, so after import they are *assumed*
to match your config (recorded, never compared, never forcing a replace).
`aws_iam_role_name` / `aws_iam_policy_name` are likewise reconciled by a
normal update on the next `apply`.

### Known behavior worth knowing

- **Onboard is never auto-retried on a 5xx, timeout or connection error.**
  Such a failure doesn't show whether the tenant was created, and re-sending
  a successful create only produces a misleading "already exists" conflict.
  Instead the provider re-lists tenants and decides: if the tenant exists and
  is ACTIVE it is adopted into state and any differing display name /
  external ID is synced via the update API; if it is INACTIVE you get an
  "already exists and is in inactive state — contact support" error; if it is
  not found you get an error with recommended actions (wait and re-apply, or
  check the dashboard and `terraform import`). An "already exists" error on a
  later apply means the same thing: `terraform import` the account.
- Onboard/update/deboard can take a while to show up in `lucidity_tenants` —
  a `terraform apply` will retry for up to 150s before erroring; a genuine
  success sometimes still needs a manual re-`apply` past that window.
- `skip_cloud_permission_check = true` skips the IAM-*permission* check
  only — it does **not** skip Lucidity's baseline cloud-account-reachability
  validation, which still runs regardless of this flag. An unreachable or
  invalid cloud account fails onboarding either way.
- Changing `aws_iam_role_name` or `aws_iam_external_id` is re-validated by
  Lucidity (it assumes the role), so a typo or a trust policy that wasn't
  updated first fails the apply. `aws_iam_policy_name` and the display name
  are not independently verified.
- A 401 from Lucidity on those updates doesn't say which check failed, so the
  error lists every possible cause (token, role name, trust policy, external
  ID, policy, permissions boundary/SCP, account ID, IAM propagation) to work
  through.

Full test evidence: [docs/qa-testing/account-management.md](docs/qa-testing/account-management.md).

## Lucidity Temporary Buffer Management

Adds temporary free space to a Lucidity-managed instance for an operation
that needs it — typically a database restore or a data migration — without
changing the instance's scaling policy. Two objects: the
`lucidity_temp_buffer` resource and the `lucidity_temp_buffer` data source.

```hcl
resource "lucidity_temp_buffer" "orders_db_restore" {
  instance_identifier {
    cloud_provider            = "AWS"
    cloud_provider_account_id = "123456789012"
    instance_id               = "i-0abcd1234efgh5678"
  }

  request_buffer_size_in_gib = 50
}
```

| Step | What the provider does |
|---|---|
| `terraform apply` | Requests the buffer, then polls its status every 30s until ACTIVE (up to 30 minutes) |
| Restore runs | Outside Terraform, once apply has finished |
| `terraform destroy` / remove the block | Revokes the buffer; the instance returns to its original scaling policy |

### Known behavior worth knowing

- **A buffer costs money until it is revoked.** Lucidity does not revoke it
  automatically. Remove the resource (or use `count` on a variable) once the
  operation is done.
- **Only one buffer per instance.** A second request for the same instance
  fails with a conflict.
- **Changing the size or the instance replaces the buffer** (revoke, then a
  new request). See "Why changes replace the buffer" below. Don't change
  them while a restore depends on the buffer, and don't use
  `create_before_destroy` on this resource.
- **Changing `request_id`** only updates state; the existing buffer is left
  alone.
- **Azure** needs `resource_group`, and `instance_id` may be the VM name.
- **A request is never duplicated on retry.** A `request_id` is always sent
  (generated if you don't set one), so a retried request after a server
  error is deduplicated by Lucidity.
- **A buffer that ends FAILED, or is still PROVISIONING after 30 minutes,**
  fails the apply but stays in state as tainted, so the next apply (or a
  destroy) revokes it instead of leaving it to bill.
- **A buffer revoked outside Terraform** is dropped from state on the next
  refresh; the next apply requests a new one if the resource is still in
  your configuration.
- **Import** takes the buffer ID: `terraform import lucidity_temp_buffer.<name> <buffer-id>`.
  The instance ID is read back; the other inputs are assumed to match your
  configuration.

### Keeping the buffer ID

Lucidity returns a buffer's ID **only once**, in the response to the request
call, and has no way to look it up afterwards (no list, no search by
instance or request ID). Every later call (status, revoke, import) needs it.
The provider handles this as follows:

- **It saves the ID to Terraform state** as soon as Lucidity returns it,
  before waiting for ACTIVE. Even if the wait fails, destroy can still
  revoke it.
- **It recovers a lost response.** If the request reaches Lucidity but the
  response doesn't come back (timeout, dropped connection, server error),
  the provider re-sends the same request with the same `request_id`.
  Lucidity documents `request_id` as its deduplication key, so this returns
  the same buffer rather than creating a second one.
- **Use a stable `request_id`** (e.g. `restore-orders-db-2026-10-23`)
  rather than letting the provider generate one. If an apply fails after
  Lucidity received the request, re-applying with the same `request_id` gets
  the same buffer back. With a generated ID, it would fail with a conflict
  instead.
- **Expose it as an output** if anything outside this configuration needs
  it, for example a restore script or a later `terraform import`:

  ```hcl
  output "restore_buffer_id" {
    value = lucidity_temp_buffer.orders_db_restore.buffer_id
  }
  ```

### Why changes replace the buffer

Lucidity's temporary buffer API has three calls: request, check status and
revoke. **There is no call to resize or modify an existing buffer**, so the
only way to apply a new size is to revoke the old buffer and request a new
one. Terraform shows this as a replacement in `plan`.

- **What the provider does to make replacement safe:** destroy waits until
  the old buffer reads REVOKED (up to 10 minutes) before the new one is
  requested, because Lucidity allows one buffer per instance.
- **What it can't avoid:** between the revoke and the new buffer becoming
  ACTIVE, the instance has no buffer.
- **A true in-place resize needs a new API call from Lucidity.**

### API documentation notes (temporary buffer)

Differences between Lucidity's API docs
([apidocs/legacy/temp-buffer/temp-buffer.md](apidocs/legacy/temp-buffer/temp-buffer.md))
and this provider that affect users:

| Topic | API docs | This provider |
|---|---|---|
| Resize or modify | No call exists | Replacement (above) |
| Find a buffer later | No list or lookup; the ID is returned once | Saves it to state; recovers a lost response by `request_id` (above) |
| Automatic revoke | None: "the buffer will continue incurring costs until manually revoked" | None either. Remove the resource when done. |
| Cancel a request | Not possible: wait for ACTIVE or FAILED, then revoke | Destroy during PROVISIONING waits, then revokes |
| Revoking a FAILED buffer | Not described | Tries to revoke; if that fails, warns and drops it from state |
| Response format | Bare JSON (`{"bufferId": ...}`); errors as `{code, message, details}` | Accepts both bare and wrapped responses |
| Error codes | Only HTTP statuses are documented (400, 401, 404, 409) | Errors are recognised by status |
| Size limits | "Typically 1 GB to 1 TB", varying by cloud and instance type | Only checks the size is at least 1 GiB |
| Rate limit | 50 requests per minute | No limiter; at most 10 calls at once, and status is polled every 30s. Many buffers in one apply could hit the limit. |
| Status fields | Instance ID, status, free space, failure reason; not cloud, account, resource group or size | After import, those inputs are assumed from your configuration |

before this provider can fully close them. Tracked as Lucidity internal JIRA tickets; this
provider's behavior will be updated once each ships. Should be backwards compatible.

| CSEN-3819 | Return distinct error codes for different cloud-account onboarding validation failures. |

### Shipped

| Ticket | Improvement | Provider behavior |
|---|---|---|
